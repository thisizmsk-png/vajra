# Vajra v0.6: knowledge ledger and real parallelism

These ideas come from Kiro Crew, Kiro specs and steering, Beads, claude-mem, Letta, Codex memories, Graphiti and Claude Code agent teams (research of 2026-10-11). Build them after v0.5 lands.

This plan **changes v0.5 rule 5**. Native auto memory stays for user preferences only. Vajra gets its own store for project facts, decisions, lessons and deliveries, each record carrying where it came from, because native memory deliberately skips anything that can be derived from the code or git history.

## Build order

1. **Knowledge ledger** (`scripts/vajra_kb.py`, stdlib sqlite3)
   - **Storage:** `~/.claude/vajra/kb/<project-id>/`. The project id is the sha256 of the git common dir, so every worktree of a repo shares one store.
   - **Files:**
     - `events.jsonl`: the source of truth. It is append-only and HMAC-chained.
     - `kb.sqlite`: an FTS5 index built from the events. It can always be rebuilt.
     - `INDEX.md`: a readable summary of at most 150 lines.
     - `pending/`: proposed records waiting for approval.
   - **Record types:** decision, fact, lesson, delivery and pitfall.
   - **Record fields:** `scope` (paths and agent), `applies` (always or on_topic), `source` (user, verified or proposed, with evidence), plus `valid_from`, `invalid_at`, `superseded_by` and `expires`.
   - **Commands:** `add`, `search`, `show`, `supersede`, `retire`, `restore`, `prime --budget`, `rebuild`, `export`, `gc`, `doctor`.
2. **Write gate**
   - **Refused outright:** any write that contains a secret (cloud keys, private keys, tokens, JWTs, high-entropy blobs), any write that matches injection patterns, and anything over the size caps. Each refusal is audit-logged as a hash.
   - **Trust tiers:**
     - `user`: only from a `/vajra remember …` prompt.
     - `verified`: only when it links to green verify-work evidence for the current tree.
     - Everything else goes to `pending/` and needs `atman.sh approve kb-<id>`.
   - **Skipped sessions:** proposals are not taken from sessions that touched sensitive paths, or (by default) from sessions that used web or MCP content.
   - **Protection:** `kb/` is a protected path, so agents can only change it by calling the script.
3. **Automatic read-back**
   - **Session start:** SessionStart runs `prime`, which lists the always-apply lessons and recent decisions as one-line pointers wrapped in `<untrusted-data>`.
   - **On each prompt:** the router adds the top 3 BM25 hits.
   - **In deliveries:** the Understand phase of `vajra-deliver` searches the knowledge base.
   - **Full records:** fetched with `show <id>` when needed.
4. **Automatic write-back from deliveries**
   - **When:** only on `done`, with the verify-work evidence attached.
   - **What:** one delivery record, the plan's decisions, and one lesson for each fix-loop round that went from failing to passing. Anything unverified goes to `pending/`.
5. **Task graph** (`scripts/vajra_tasks.py` on `campaigns/<slug>/tasks.json`)
   - **Task states:** pending, ready, claimed, in_progress, done, blocked, question and failed.
   - **Commands:** `deps`, `validate` (catches cycles and unknown agents, exits 2), `ready`, atomic `claim` (mkdir lock), `report`, `close --evidence`, and a Mermaid `graph`.
   - **Rule:** only the script changes a task's status.
6. **Wave scheduler in `vajra-deliver`**
   - **Grouping:** tasks are sorted by dependency into waves, and tasks whose file globs overlap go into separate waves.
   - **Limits:** `maxInFlight` defaults to 4, so waves replay the same way on resume.
   - **Idempotent workers:** each worker first checks its task's status.
   - **Review loops:** at most 3 rounds, and no self-loops or A→B→A loops.
7. **Structured worker reports**
   - **Shape:** `{status: progress|done|blocked|question, summary≤500, artifacts, evidence_cmds}`.
   - **Who decides done:** a worker's `done` is only a claim. The task closes only when vidura's verdict passes the code check.
   - **What gets passed on:** artifact paths, never one worker's prose pasted into another agent's prompt.
8. **Declarative crews**
   - **Spec:** `crews/<name>.json` holds the lead, members, phases, loops, governance and `protected_actions: return_plan`.
   - **Check:** `vajra_crew_check.py` validates each spec.
   - **Compile:** `install.sh` turns every spec into `~/.claude/workflows/vajra-crew-<name>.js` from one template.
9. **Forgetting**
   - **Nothing is deleted silently:** supersede and restore work through tombstones.
   - **Dedup on add:** a new record whose title overlaps an existing one (Jaccard ≥ 0.6) is merged instead of added.
   - **Old deliveries:** after 90 days they fold into monthly summaries.
   - **Stale facts:** a fact whose paths are gone is flagged, not injected.
   - **Hard delete:** only through the user's explicit `/vajra kb forget`.
10. **Spec artifacts**
    - **Files:** `campaigns/<slug>/spec/` holds `requirements.md` (EARS), `design.md` and `tasks.md`, each with `_Requirements:_` links back to the requirements.
    - **Gated mode:** `--gated` splits a delivery into separate workflows, with your approval between them.
11. **Native per-agent memory:** `memory: project` for vidura, bhishma and arjuna, so they record recurring defect patterns.
12. **Background consolidation:** proposes merges and promotions into `pending/`. Build it last, once there is real data.

**Not taken on as dependencies:** Graphiti/Neo4j, mem0, hosted claude-mem, or default embeddings. Semantic search can come later as an optional `--index best` mode.

**Cleanup:** move the unused v0.4 store at `~/.claude/vajra/memory/` into `kb pending/`, or flag it in `vajra doctor`.
