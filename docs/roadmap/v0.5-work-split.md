# v0.5 work split and contracts

Four workstreams run in parallel on branch `v0.5-real`. Each owns its files and edits nothing else.

Rules for every workstream:
- Don't commit or run `scripts/generate-manifest.sh` (the lead does both).
- Don't modify the real `~/.claude/settings.json`, `~/.claude/workflows/` or `~/.claude/vajra/`. Test with `HOME=$(mktemp -d)`.
- Claude Code 2.1.296 docs are the reference: https://code.claude.com/docs/en/hooks and https://code.claude.com/docs/en/workflows

## Shared contracts

- **Hook payloads:** JSON on stdin. Fields: `session_id`, `transcript_path`, `cwd`, `hook_event_name`, `tool_name`, `tool_input`, `tool_response`, `agent_type` (in subagents). A hook blocks with exit code 2 or deny JSON. Any other non-zero exit does not block.
- **Router (C → A):** `scripts/vajra_route.py` reads the UserPromptSubmit JSON on stdin. It prints nothing, or one JSON object:
  `{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":"…"}}`
  - It acts only on prompts starting with `/vajra` (case-insensitive), unless `config.routing.suggestOnAllPrompts` is true.
  - It appends one line per routed prompt to `~/.claude/vajra/routing-log.jsonl`:
    `{ts, session_id, prompt_sha256, words: [up to 20 lowercased words], route: {tier, skill, agent, pattern}, suggested: [every skill shown, top first]}`
  - It never fails the prompt.
- **Practice log (D, read by D and C):** `~/.claude/vajra/practice-log.jsonl`. Written by `hooks/post-tool-use.sh` for PostToolUse and PostToolUseFailure. Fields:
  `{ts, session_id, event, tool, skill (tool_input.skill for Skill calls), agent (agent_type or null), outcome: success|failure, error_sha256, seq, prevHmac, hmac}`
  - It stores no raw error text.
- **Campaigns (B, called by A):** `scripts/vajra-campaign.sh`. State lives in `~/.claude/vajra/campaigns/<slug>/`: `campaign.json`, `features.json`, `progress.md`, `checkpoints/`.
  - `active --brief` prints one line or nothing.
  - The script reads the HMAC key itself, so the key never enters model context.
- **Workflows (B, installed by A):** `workflows/vajra-<crew>.js` for `feature-build`, `security-audit`, `incident-response`, `architecture-review` and `sabha`. `install.sh` copies them to `~/.claude/workflows/`.
- **Atman CLI (D, referenced by C):** `scripts/atman.sh status|review|approve <id>|reject <id>|log|pause|resume|propose`.
  - Proposals live in `~/.claude/vajra/proposals/`.
  - Nothing writes to `config/` or the skill core automatically.
- **Tests:** each stream adds `tests/**/run-*.sh` scripts that exit non-zero on failure. Stream C's `tests/run-all.sh` globs them all.

## Product goal (added by the owner): ask in, finished product out

`/vajra <any ask>` runs autonomously by default. The user shouldn't have to say which crew, agent or step to use.

**Stream B** writes `workflows/vajra-deliver.js`, the autopilot. It runs these phases:
1. **Understand.** Restate the ask, define acceptance criteria and scope, and list assumptions. If something is ambiguous, pick the most reasonable reading and record it. Return `need_input` only when the ask can't be done without the user.
2. **Plan.** Break the work into tasks with an owner agent each, chosen from the roster by charter, and dependencies between them.
3. **Execute.** Run independent tasks in parallel. Writers run in worktrees. Reuse the crew workflows' patterns.
4. **Verify.** vidura runs real checks against every acceptance criterion. Reviewers (arjuna, plus bhishma when the work touches security) review read-only.
5. **Fix loop.** Repeat until every criterion has passing evidence, up to 3 rounds.
6. **Deliver.** Merge the worker branches into one local branch and write a delivery report: what was built, evidence per criterion, how to run it, and open risks.

It never performs protected actions. A deploy, push or PR comes back as a ready plan for the user's approval. It also records progress in a campaign via `vajra-campaign.sh` so a long ask can be resumed.

**Stream C:** in SKILL.md and docs, a bare `/vajra <ask>` launches the `vajra-deliver` workflow by default, with no manual steps. The router uses the ask only to suggest which crews and skills the plan should use. Explicit subcommands still work.
